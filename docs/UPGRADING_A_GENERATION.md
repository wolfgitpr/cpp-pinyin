## 生成的数据文件：行尾策略与逐字节稳定（2026-10-16 实测）

换代时除了"哪些文件要改"，还要注意**生成物本身的行尾**。实测：词典仓的 `common.py` 用文本模式写
`format.txt`，Windows 上 `\n` 变成 `\r\n` ⇒ 生成的是 **3 字节**，而入库副本是 **2 字节（LF）**；
两边在 `check_drift` 的逐字节比对下必然打架（而引擎侧体检会容忍 `\r`，所以**加载测试抓不到它**）。
修法：生成器显式写 LF（`open(..., newline='\n')`），与本仓 `csharp/tools/emit_build_info.py` 的既有
约定同源。**教训**：数据类生成文件也要写明行尾策略，否则"跨平台字节稳定"这句承诺只在一半平台上成立。

## 2026-10-18：默认风格改为单一权威（D4；公开名新增 `defaultStyleOf`）

- **`Dialect::defaultStyle` 字段已删除**（公开插件面 18 → 17）。默认风格改由 `styles[]` 里
  `isDefault == true` 的那一项决定，读取它的公开函数是新增的 `cpp_pinyin::v2::defaultStyleOf`
  （`core/Types.h`，已进冻结名单：37 个公开名 = 37）。
- **迁移**：删掉 `d.defaultStyle = 8;`，改为在表里标 `true` ——
  `d.styles = {{"normal", 0, false}, {"tone3", 8, true}};`（内置两方言本来就这么写着）。
- **为什么要改**：两个字段说同一件事，且消费者不同 —— `resolveStyle` 读字段、
  `cppp2_style_list` 读 `isDefault` 标记 ⇒ 插件可以"发布一个默认、渲染另一个"，而两者之间
  没有任何门禁比对。
- **判据**：`check_public_names`（37 = 37）· `check_bindings`（插件面 17）·
  `test_style_table`（恰好一个 `isDefault`，且等于内置方言的默认）。

## 2026-10-18（同批次）：变调改为方言属性（D10；新增公开名 `ToneSandhiPass`）

- `Dialect` 新增 `ToneSandhiPass toneSandhi = ToneSandhiPass::None`（插件面 17 → 18，公开名 37 → 38）：
  变调**不是**所有方言共享的 core 概念，而是方言自己的属性。普通话把它声明为 `Mandarin`，粤语保持 `None`。
- **C 面签名变了**：`cppp2_apply_tone_sandhi` 现在第一个参数是 `const cppp2_engine *`。理由：过去它没有方言
  维度，任何 result 传进来都会套用普通话的 不/一 规则，而 jyutping 与拼音**形状一样**（字母+声调数字），
  没有任何形状测试能区分 ⇒ 对粤语结果是静默错答案。现在它问方言：声明了就跑，没声明返回
  `CPPP2_ERR_INVALID_ARG` 且不改动任何一行。
- **迁移**：C 调用方多传一个 engine；C++ 侧不变（`applyMandarinToneSandhi` 仍在）；Python/C# 壳已同批更新
  （它们的 `sandhi=` / `ToneSandhi()` 接口签名不变，只在内部把 handle 传下去）。
- **将来加方言**：新的变调趟 = 新枚举值 + **新符号** `cppp2_apply_<dialect>_sandhi`（2.x 允许加符号），
  永远不改已有签名。
