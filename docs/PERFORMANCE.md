## 0. 一句话结论

**整个 `[batch]` 工作负载 = 1272 ms（min-of-5）。** 四条数据集准确率 14 次运行逐字稳定；
性能噪声地板在 **min 判优** 口径下为 **1.46%**，因此 **10% 的验收阈值是可以分辨的** ——
但**前提是必须按 §1 协议测量，不能引用测试内打印的吞吐**（§3 给出反例）。

## 1. 测量协议（强制）

任何"性能提升/退步"的断言必须走完六步（P1–P6），缺一步即无效。

| 步骤 | 要求 | 依据（实测） |
|---|---|---|
| **P1 等价门禁** | 两侧四条准确率**逐字相同**，否则计时对比作废 | 准确率不同 = 做的工作不同，比时间无意义 |
| **P2 交错** | A/B **逐样本交替**（奇偶轮换序），不是先跑完 A 再跑 B | 热漂移/后台负载等量落在两侧，不系统性偏袒先跑方 |
| **P3 取最小** | 判优用各侧 **min** | 实测：中位数口径 A=1272/B=1355（差 6.5%），min 口径 A=1227/B=1209（差 1.46%）。尖峰（一次 1693 ms，高 38%）只污染中位数 |
| **P4 轮数** | **≥7 轮**（=14 样本/侧） | 零效应对照实测：7 轮下 min 落差收敛到 1.46% |
| **P5 阈值** | 加速比 ≥ **1.10** 才接受，< 1.10 直接丢弃 | 用户既定纪律；1.46% 噪声地板远低于 10%，阈值可分辨 |
| **P6 独占机器** | 跑 A/B 期间**不要并行跑构建/门禁/其他压测**；有疑问就重测一轮 | 实测反例（2026-09-23）：两个后台构建与 A/B 并发时测出 `1.1225` 的"加速"，机器空闲后重测（9 轮）是 `1.0045`，同批零效应对照 `0.9977` —— **负载漂移会伪装成收益** |

### 1.1 工具自证（改测量工具后必做）

**零效应对照**：把 A、B 指向**同一个二进制**，判优结论必须是"未达阈值"。实测（7 轮 14 样本）：

```
侧      min     中位数      max
A      1227      1272      1693
B      1209      1355      1434
-> min 落差 1.46%，判优结论「未达 10% 阈值」  符合预期
```

**已修复的两个测量陷阱**（本项目真实踩到）：

1. **测试内吞吐不可用**：`test_batch_accuracy.cpp` 经 `fmtRate` 只打印 **2 位有效数字**，
   `1.1M`→`1.2M` 的步进即 **8~9%**，与 10% 阈值同量级。本文件改用**进程 wall-clock 减启动开销**
   （启动开销实测 42 ms，占 3%）。
2. **PowerShell 5.1 的 `ProcessStartInfo` 没有 `ArgumentList`**：赋值静默失效 ⇒ 子进程拿不到过滤
   参数、跑的是无过滤全量测试，测出的"启动开销"其实是整套测试耗时（2841 ms，虚高 68 倍）。
   现每次测量都**校验 Accuracy 条数与退出码**：空过滤必须 0 条 + 退出码 2，真跑必须命中条数 + 退出码 0。

### 2.4 基准工具的测量口径（2026-09-29 起，`tests/benchmark.cpp`）

`Benchmark` 现在同时是**给人看的表**和**给机器读的报告**：`--json <path>` 写一份带 schema 号的
报告，`--repeat N` 每个用例测 N 遍取最好一遍，`--compare <baseline.json>` 把本次与归档报告逐用例
对比并打印一行可 grep 的汇总，`--brief` 只保留每用例一行。即使不存 JSON，每次运行也都会打印一行
`BENCH ... index_geomean_min_us=...`，所以任何一次运行都留下可对比的数。

下表每条都实测过（本机，同一二进制），不是从 §3 的结论推出来的：

| 决定 | 实测依据 |
|---|---|
| 对比用 **min**、不用中位数 | 同一二进制 8 次运行：中位数在用例之间波动最大 **25.11%**，min 只有 **0.55%**。与 §3「中位数/均值：尖峰污染」和 §1 的 min-of-N 口径（P3 取最小）一致，但这两组数是在本工具上直接量出来的 |
| 用例迭代次数按 **~50 ms/用例** 定 | 95 字用例原本只跑 200 次（4.4 ms），5 次运行实测 **22.4 → 35.4 µs（58%）**；改成 2000 次后 8 次运行最大波动 **4.55%**，整套耗时仍只有约 3 s（把一次 22 µs 的调用只测 200 次，测的是调度而不是代码） |
| 判"退化"的带宽 **±6%**（词典加载 ±20%） | 8 次运行的非噪声用例最坏 4.55%、次坏 3.57%；词典加载单独看 11~19%。带内记为 `tied`，带宽随输出打印，不藏在代码里 |
| 汇总指数用 min 且**排除词典加载** | 词典加载与其他用例不是同一量级（20 ms vs 6 µs），放进几何平均会盖住其余；排除后 5 次运行指数波动 **0.73%** |
| 不设时间门禁 | 上面两条波动就是理由：门禁会在噪声上失败。CTest 只做 `BenchmarkSmoke`（跑通 + 留一份 JSON），对比由人看 |

`--compare` 还会检查基线与本次的 `--repeat` 是否一致：best-of-N 会把数字压低，混着比会把
"少测了几遍"读成"变快了"，此时标记行给 `repeats_match=0`。词典加载的两个用例在报告里带
`"noisy": true`（成本由 I/O 与页缓存决定，不是我们的代码），它们进表、进对比，但不进汇总指数。

**这个工具的效力边界**：它是开发期的快速读数，`--repeat` 是**同一进程内的 best-of-N**，与 §2.0／§1
的板上前提（独占机器、9 轮 × 4 passes 逐样本交错、P2/P3/P4/P6）不是一回事。能不能作为收益证据，
仍按 §1 的协议判：本工具的 ±6% 只是"这次没看出差别"，不是"没有差别"。

## 3. 不可用于判优的测量方式

| 方式 | 问题 |
|---|---|
| 测试内打印的 `xxK sent/s` | 2 位有效数字，量化步进 8~9% |
| 单次运行读数 | 同二进制两次跑差 12~22% |
| 中位数/均值 | 尖峰污染（实测 max 比 min 高 38%） |
| 不校验参数生效的外部计时 | PS 5.1 `ArgumentList` 陷阱（§1.1） |
| 同进程内交替跑两个版本 | 本项目不存在此场景（库静态链进 exe），A/B 必须是两个不同 exe |

### 4.2 成本归属（实测，替代不可用的 gprof）

**⚠ 前提更正**：本节早期版本称「82%/84% 未归属」，那是**把 `queryRaw` 整体当黑盒**得出的。

> `§4.2.0` 只留结论；插桩相位表与自证过程的记录已不在仓库里。
#### 4.2.1 已实施的优化（commit `原 846d944`）

**词组两层合并在装载时完成，窗口热路径从两次查表降为一次。**

C-22 曾让 `emitPhrase` 采用「先查用户层、再查内置层」，于是只有 99 条的用户层被
**无条件探测 1035 万次**，其中约 99.1% 必然落空。变体实验（同一尝试序列，只改层与顺序）：

| 变体 | 耗时 | 查找数 | 命中数 |
|---|---|---|---|
| mode0 现状 user→builtin | 285.0 ms | 10,351,939 | 93,881 |
| mode1 颠倒 builtin→user | 266.0 ms | 10,351,939 | 93,881 |
| mode2 无用户层（上界） | 139.1 ms | 10,355,578 | 92,800 |
| **mode3 装载时合并为单表** | **141.6 ms** | **10,351,939** | **93,881** |

颠倒顺序只省 1.7% **且不安全**（用户层本意是覆盖内置，颠倒会反转覆盖关系）；
**装载时合并省 12.6%，且 mode3 的查找数与命中数与 mode0 完全相同**——合并只省掉白查。

**协议 A/B 判定（P1–P5，11 轮逐样本交错，min 判优）**：

| 口径 | A（改前） | B（改后） | A/B |
|---|---|---|---|
| min | 1184.4 ms | **1038.5 ms** | **1.1404（B 快 12.3%）** |
| med | 1238.6 ms | 1075.3 ms | 1.1519（15.2%） |

P5（≥1.10）**通过**。工具自证：零效应对照（A=B 同一二进制）该口径下 min 比值
0.99~1.02、噪声幅度 12~19%（**注意：此口径噪声远大于 §1 记录的 1.46%**，
故单次读数绝不可用于判优）。
准确率四条**逐字未变**；全量 624 断言 / 91 用例全绿；C-21 与 C-22 语义均已回归验证。

**遗留的架构张力（未解决，供 v2 决策）**：合并后 `loadUserDict(clear=true)` 需要
**从 `phrases_dict.txt` 重读内置条目**（因为 `loadDict` 不在装载前 clear，必须先 drop）。
实测耗时可忽略（`rebuildPhrases` 约 2 ms，且 `loadUserDict` 不在热路径上），但语义上
「清空用户层会触发一次磁盘重载」并不优雅。v2 若引入 dict 层缓存/预编译格式，应顺带
消除它。

#### 合并的正确性证据：覆盖顺序是逐字精度攸关的

`user_dict.txt`（99 条）与 `phrases_dict.txt`（6026 条）有 **32 个同名键**，且这 32 个
**读音全部不同**（`std::unordered_map` 取值先到者胜）。因此「用户覆盖内置」不是无害的
可选优化，而是**真实语义**。实测风险面：

- 32 个同名键中 **26 个真的出现在 `cpp_dataset` 语料里，覆盖 2,600+ 行**——
  `中的`（952 行，内置 `zhòng,dì` vs 用户 `zhong1 de5`）、`到了`（691 行）、
  `面的`（300 行）、`都会`（120 行）、`成都`（100 行）等；
- 故若按 §4.2.1 变体实验里「颠倒顺序只省 0.4%」的表象去改顺序，会**静默改错 2,600+ 行**
  ——这是本该避免的错法：**计时差异小 ≠ 语义差异小**。

合并实现保留「用户条目赋值覆盖内置」，并由以下证据守护：四条准确率逐字未变、全量
624 断言 / 91 用例全绿、C-21 与 C-22 语义回归探针通过（`clear=true` 后纯内置条目
`上当` 仍为 `shang4 dang4`，用户条目 `一宿` 正确消失）。

**顺带记录该用户的 `user_dict.txt` 数据问题（源数据缺陷，本批未改）**：8 条含「都」的
地名把 `dū` 写成 `dou1`（京都/国都/陪都/乐都/花都/曾都/大都/上都/中都），共影响约 198 行。
`军团` → 应为 `du`。这些属 DATA_FIX 范畴，不是代码缺陷。

#### 合并后的成本归属复测（逐段复刻实测，`本地留档（未入库）：perf/probe_recon.cpp`）
把引擎的逐字符工作**按源码原样复刻**再分别计时（min of 7，同一语料），得到：

| 复刻段 | 耗时 | 折合 | 占 1140 ms |
|---|---|---|---|

| d) 其中仅 `applyTone` + 转换部分 | 46.1 ms | 19.9 ns/字符 | 4.0% |
| c) 其中仅 `charUtf8` 转换部分 | 19.4 ms | 8.4 ns/字符 | 1.7% |
| a) 不在词典分支（含 **2 次重复** UTF 转换） | 15.5 ms | 6.7 ns/字符 | 1.4% |
| e) `mergeWithPositions` 的每字符转换 | 15.2 ms | 6.6 ns/字符 | 1.3% |
| f) 每字符构造一个 `u16string`（`splitInput` 形状） | 0.1 ms | 0.0 ns/字符 | 0.0% |

语料构成：**不在词典 8.5%（197,288）、快路径 51.6%（1,192,689）、开窗 39.9%（922,786）**。

**已定位的结构性事实**：
- `splitInput`（`src/EngineImpl.cpp:189`）把每个汉字切成**独立的 `std::u16string` 元素**
  ，故 `std::vector<std::u16string>` 有 2,312,763 个元素；
- `sizeof(Syllable)` 实测 **96 字节**，故 `queryRaw` 的 `result.reserve(chars.size())`
  一次性申请约 **222 MB**；`splitInput` 的 vector 约 74 MB；
- 分配放大 38.6 倍（283 万次 / 765 MB vs 净产出 19.9 MB）与平均单次分配 **270 字节**
  （≈96×2 或 96×3 的批量结构）与此吻合；
- `applyTone` 的真实内容是 `m_toneConverter.convert({pinyin.begin(), pinyin.end()}, ...)`，
  而 `convert`（`src/ToneConverter.cpp:5`）按值收 `std::u16string`。

### 4.3 起：已否决的方向（结论）

SIMD、`reserve`、滑动窗、`-flto`、融合上界探针、结构化读数两侧报数等 20 个方向都已试过并**关闭**；
关闭它们的准入判据就是本文 §4.1/§4.2 现行的那几条，逐项的实测数字与关闭理由不在仓库里。
